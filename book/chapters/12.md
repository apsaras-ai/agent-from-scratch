# 第 12 章：State Persistence 与 Durable Execution

> **正文初稿 v0.1，待技术审稿** · 第二篇：Agent 核心架构。实验为 SQLite 单机持久化实现，不是具备分布式可靠性保证的生产 Agent Runtime。

## 12.1 为什么运行状态不能只存在内存？

前面的 Agent Kernel、Event Store 和 Workflow Engine 可以处理普通控制流，但是进程重启以后，运行状态和未完成的步骤可能丢失。对于运行数小时的 Coding Agent，状态恢复意味着至少知道任务身份、已完成步骤、下一步位置、工具调用以及外部副作用是否得到确认。

重要的区分是：**恢复状态不等于重新执行所有动作**。如果外部 API 曾经成功写入，而客户端在得到响应前宕机，再执行同样动作可能造成重复写入。

## 12.2 三种状态

- **Run State**：Created、Running、Waiting、Completed、Failed 等业务状态。
- **Execution History**：按顺序记录动作决策、工具观察和状态变更。
- **Checkpoint**：执行器可恢复的位置和必要状态快照。

这三个概念不能互相替代。Checkpoint 可能使恢复更快，但历史仍可用来审计执行过程；Event Log 记录了事实，却不保证重复运行工具是安全的。

## 12.3 SQLite 事件存储

[核心代码](../../src/mini_agent/durable_execution.py) 使用 Python 标准库 sqlite3。最小模式包含 runs、events 和 operations 三个表。

~~~text
runs(run_id, version, status, cursor)
events(run_id, version, event_id, kind, payload)
operations(run_id, op_id, state, result)
~~~

事件和当前状态投影必须在一个数据库事务中更新。本实现使用 BEGIN IMMEDIATE 和版本检查，以减少本地多个写入者之间的丢失更新。重复 event_id + 相同内容作为幂等追加；同 ID 不同内容拒绝。

### 写入不变量

- 一个 Run 的 Event Version 单调增加。
- 不能向已完成的 Run 追加普通进展。
- Cursor 不应后退。
- Event ID 不应覆盖已有的不同数据。
- 写入冲突不能悄悄重试为另一个业务决定。

## 12.4 Checkpoint 和恢复

每次成功完成一个有明确结果的步骤，应把状态和当前位置持久化。重新启动后从存储读取 Snapshot，并由上层控制器决定下一步行动。

本章的 Checkpoint 只含最小 cursor、status 和 version；没有保存完整的模型 Context、外部资源引用和真实 Worker 租约。它演示的是**持久化控制状态**，不是完整 Workflow Replay。

## 12.5 可靠执行与不可确定的外部副作用

最关键的故障窗口：

~~~text
1. Write intent to database: pending
2. Call external API
3. External API may commit
4. Process crashes before recording result
5. Restart sees pending
~~~

恢复时无法仅凭 pending 判断外部操作成功或失败。因此本章 `resume_decision` 返回 `reconcile_external_effect_before_retry`，要求查询外部系统的业务状态，或使用服务端支持的 Idempotency Key。这比“看见 pending 就再发一次”更安全。

另外，保存事件和调用外部 API 并不在同一事务中。要获得更强语义，可以研究 Transactional Outbox、Activity 幂等、补偿操作和 Worker Lease。

## 12.6 Event Sourcing 与 Durable Replay

纯状态重放只读取 Event Log 重建对象；它绝不能再次调用工具。Temporal 等 Durable Execution 系统提供 Workflow History、Activity 与重放规则，用来协调中断后的工作。真正的持久化系统还必须处理代码升级、Workflow 版本兼容、长期等待和多实例调度。

本章没有实现这些生产机制，不应称作完整 Temporal 替代品。

## 12.7 Crash Recovery 实验

[离线实验](../../examples/ch12_durable_lab.py) · [单元测试](../../tests/test_ch12.py)

~~~bash
python -m pip install -e .
python examples/ch12_durable_lab.py
python -m unittest discover -s tests -v
~~~

实验创建 SQLite 数据库，写入 run.started，记录工具 pending 状态，关闭连接模拟进程停止，再以新数据库连接恢复。恢复后确认记录仍存在；对待确认的工具不自动执行。模拟核实外部结果后记录 confirmed，再读取结果。

测试还检查 Version Conflict、事件重复、终止状态保护以及恢复后仍可读取事件记录。

## 12.8 生产差距

此实现是单机演示，还缺少：分布式 Worker Lease、Heartbeat、真正的 Checkpoint 内容、加密、跨租户授权、数据库迁移、Outbox、任务取消和异步挂起、远程故障注入，以及外部 API 幂等契约。SQLite WAL 也不应被误认为完整的多主分布式一致性系统。

## 12.9 习题

1. 实现带数据库 CAS 的 Worker Claim 和 Lease。
2. 模拟外部操作已成功但确认写入失败，验证不会直接重复执行。
3. 增加任务取消中间态与 ACK。
4. 将第 11 章 Workflow Node 状态持久化。
5. 加入 Outbox 表和可重试消息分发。
6. 设计 Workflow Code Version 变化后的恢复兼容性测试。
7. 记录每次 Model/Tool 调用的真正耗时和费用。
8. 对比 SQLite 与 PostgreSQL 的原子写入、锁和租约方案。

## 12.10 总结

可靠 Agent Runtime 的核心不只是保存当前状态，而是明确**哪些事实已经持久化、哪些外部副作用已确认、哪些动作处于未知结果**。恢复执行需要在状态、事件、Checkpoint、幂等性及外部系统协议之间建立可信边界。
