# 第 22 章：Agent Observability 与 Debugging

> **状态：正文初稿 v0.1，待技术审稿** · 第四篇：生产级 Agent Runtime 与 Infrastructure。

## 22.1 从 Agent Loop 到可诊断的运行链

前面的 Agent Kernel、Tool Runtime、Browser/Coding Agent、Scheduler 和 Outbox 都有状态信息，但一个长任务可能经过数十次模型调用、搜索、代码修改、重试与审批。单条 `tool failed` 日志无法回答：

- 哪个用户 Task/Run 触发了这次调用？
- Tool 失败是否发生在已经过期的 Lease 上？
- 是否曾被重试？重试为什么没有消除错误？
- 用户最终验收失败，是检索遗漏、模型错误还是工具越权？
- 哪一步占用主要时间？有没有并行？
- 模型是否多次生成了无效工具参数，浪费 Token？
- 能不能 Debug，而不把用户邮件、源代码或 Secret 复制到外部日志？

可观测性的目标并不是**尽可能多记录所有内容**，而是利用最少的可信元数据还原有解释力的控制过程。

~~~mermaid
flowchart TD
  U[User Task] --> R[invoke_agent]
  R --> P[plan]
  R --> M1[chat 1]
  M1 --> T1[execute_tool: denied]
  R --> M2[chat 2]
  M2 --> T2[execute_tool: approved]
  R --> M3[chat 3]
  R --> V[Independent verifier]
  V --> O{Accepted?}
  O -->|yes| OK[Verified]
  O -->|no| NO[Failed / needs evidence]
~~~

要特别保持三个平面的区别：

| 平面 | 主要数据 | 可用于什么 |
| --- | --- | --- |
| **业务事实** | Run/Event/Checkpoint、Outbox、Provider Receipt | 权威执行状态与恢复决策 |
| **遥测观察** | Trace/Span/Log/Metric | 查找失败、定位慢操作、估算成本 |
| **模型内容** | Reply、Plan、Tool Proposal | 决策与待验证的提议；不是授权或事实来源 |

Trace 可以被采样或丢失，不能用它取代第 12、20、21 章的持久化操作记录。

## 22.2 Logs、Metrics、Traces 的分工

**Log** 是一次事件的记录；**Metric** 对运行行为作有界维度聚合；**Trace** 描述同一工作流的多个操作、时间和父子关系。OpenTelemetry 官方 Primer 对这三者的互补性有清晰说明。[1]

### 22.2.1 Log

~~~json
{"kind":"tool_denied","reason":"resource_not_allowed","trace_id":"..."}
~~~

结构化错误码有利于检索与告警，但没有 Task/Trace 关联时很难解释完整因果链。

### 22.2.2 Metric

~~~text
agent_tool_calls_total{tool_kind="search",outcome="denied"}
agent_model_tokens_total{provider="synthetic",type="input"}
agent_verified_tasks_total{task_kind="research",outcome="passed"}
agent_reconciliation_pending{operation_kind="email"}
~~~

避免把 User ID、Email、Task ID、原始 URL 等高基数或敏感值放在 Metric Labels 中。

### 22.2.3 Trace 与 Span

一个 Span 至少需要：

| 字段 | 含义 |
| --- | --- |
| Trace ID | 关联一组操作 |
| Span ID | 当前操作的标识 |
| Parent Span ID | 父操作 |
| Operation | 如 `invoke_agent`、`chat`、`execute_tool` |
| Start/End/Duration | 时间边界与开销 |
| Status / Error | 正常、错误、取消 |
| Attributes | 有 Schema 约束的元数据 |
| Events | 受限的离散事件 |
| Token Usage | Provider 明确报告的计量数据 |
| Cost Estimate | 明确 Fee/Rate Card 下计算的估算值 |

Span 的 `status=ok` 只代表该操作按对应技术层的契约完成，**并不等于整个 Agent Task 已通过独立验收**。

## 22.3 OpenTelemetry GenAI 语义约定

### 22.3.1 生产数据路径

~~~mermaid
flowchart LR
  API[Agent API] --> W[Agent Worker]
  W --> M[Model Gateway]
  W --> T[Tool Runtime]
  W --> S[Sandbox]
  API -.-> O[OTel SDK]
  W -.-> O
  M -.-> O
  T -.-> O
  S -.-> O
  O --> C[Collector: sampling, redaction, quotas]
  C --> D[Trace/Metric/Log Backends]
~~~

这是**生产参考结构**，不是本章实际启动的服务。本章只完成最小数据模型、有限字段和离线 JSONL Export/Read。

OpenTelemetry 官方将 GenAI Agent、Tool Spans 的部分语义规范标为 **Development**，因此应为部署版锁定 SemConv/SDK 版本，并核对字段兼容性。[2][3]

### 22.3.2 有意义的字段

| 语义属性 / 本章映射 | 示例 | 实际意义 |
| --- | --- | --- |
| `gen_ai.operation.name` | `chat` | 本章存储为 `SpanSnapshot.operation`，尚未实现 OTLP 属性转换 |
| `gen_ai.provider.name` | `synthetic` | 可信模型适配器的 Provider Label |
| `gen_ai.request.model` | `fixture-model` | 可信 Host 选择的 Model |
| `gen_ai.usage.input_tokens` | 100 | 模型 Input Token，包括 Provider 已计入的 Cache |
| `gen_ai.usage.output_tokens` | 20 | Output Token |
| `gen_ai.tool.name` | `lookup` | 可信 Tool Registry 的受控名称 |
| `agent.verification.passed` | `true` | 自定义业务验收字段，只供可信 Verifier |
| `agent.verification.reason` | `host_fixture_checked` | 自定义有限理由 |
| `agent.workflow.phase` | `completed` | 自定义 Workflow 标签 |

不能将本书的本地 `SpanSnapshot` 误认为官方 OTLP `Span`，也不能无条件把所有 Tool/Model Usage 当作统一账单。

### 22.3.3 默认不要录制内容

OTel GenAI 文档对 `gen_ai.input.messages`、`gen_ai.output.messages`、System Instructions 和 Tool Arguments/Results 明确提示敏感信息风险。[4]

其中可能包含：私有仓库代码、浏览器 Cookie、用户邮件、身份凭证、系统提示词、工作文档和商业数据。即使在业务数据库里得到保护，直接写到 Trace Backend 也可能扩大副本、保留时间与访问范围。

**本章采用 Allowlist，而不是事后 Regex 模糊脱敏。** 只有事先声明的结构化字段可以进入 Span，所有其他 Key 被拒绝。

## 22.4 W3C Trace Context 与信任边界

W3C `traceparent` Version 00 由四部分组成：[5]

~~~text
traceparent: 00-<32 lowercase hex trace-id>-<16 lowercase hex parent-id>-01
~~~

- Version 是 `00`；
- Trace ID 为 16 字节，不能全零；
- Parent ID 为 8 字节，不能全零；
- Trace Flags 包含采样建议。

本章提供：

~~~python
parse_traceparent(header)
format_traceparent(trace_id, span_id, sampled=True)
~~~

严格解析 Version 00 格式，但不实现未来版本、`tracestate`、`baggage`、远端 Parent/Link 接收或完整跨服务传播。生产请使用官方 W3C/OpenTelemetry Propagator。

### 22.4.1 Trace ID 不是权限

攻击者即使知道合法 Trace ID，也不应因此拥有查看其他用户 Trace 或调用私有 Tool 的权力。

~~~text
Trace Context   → correlation
Principal/IAM   → authentication
Tool Policy     → authorization
Verifier        → actual task acceptance
~~~

不要根据 Header 的 `sampled=1` 决定是否绕过访问控制，也不能让 Trace ID 充当跨租户查询令牌。W3C Trace Context 本身并不提供这样的安全语义。[5]

## 22.5 Span 的父子关系与并发

### 22.5.1 同步嵌套

~~~python
tracer = TraceRecorder()
with tracer.span("invoke_agent"):
    with tracer.span("chat"):
        call_model()
    with tracer.span("execute_tool"):
        call_tool()
~~~

在本章真实代码中，`TraceRecorder` 使用 `ContextVar` 保存当前 Span ID，创建子 Span 时关联该 Parent。

### 22.5.2 `asyncio.gather`

~~~python
async def lookup(name):
    with tracer.span("execute_tool",
                     attributes={"gen_ai.tool.name": name}):
        await trusted_async_io()

with tracer.span("invoke_agent"):
    await asyncio.gather(
        lookup("search"),
        lookup("compile"),
    )
~~~

两个异步分支必须共享同一个 Root，但不会互为 Parent。测试会验证 Span IDs 唯一、Parent ID 正确，且两个分支都关闭后才能导出完整 Trace。

### 22.5.3 跨线程/进程/主机

`ContextVar` 不自动建立任意远程服务的分布式 Trace。在不同线程池、远程 Worker、MicroVM 或 HTTP 请求间应使用经过信任审查的 Explicit Context Propagation。

采样标记和 Header 仍属观测建议，不具有 IAM 权限。

## 22.6 记录时间：Wall Clock 与 Monotonic Clock

本章同时记录：

~~~python
start_wall_ns = time.time_ns()
start_mono_ns = time.monotonic_ns()

duration_ns = time.monotonic_ns() - start_mono_ns
end_wall_ns = time.time_ns()
~~~

Wall Clock 便于跨服务关联，Monotonic Clock 更适合计算单机耗时，避免 NTP/手动时间调整干扰。

### 22.6.1 Inclusive 时间与 Critical Path

~~~text
invoke_agent:   100 ms
  model:        60 ms
  tool:         30 ms
  verify:       10 ms
~~~

不能把父 Span 与子 Span Duration 直接相加当作总耗时。

对于并发：

~~~text
root:         100 ms
  tool_a:      50 ms (0-50)
  tool_b:      60 ms (0-60)
~~~

两个子 Span 重叠，总执行时间不等于 110 ms。真正 Critical Path 需要结合 DAG 和重叠关系计算；本章的 `slowest_child` 只是寻找最长的子 Span，不是严格关键路径或根因判定。


## 22.7 从零实现隐私优先的 TraceRecorder

核心代码：[`src/mini_agent/observability.py`](../../src/mini_agent/observability.py)。

### 22.7.1 安全元数据白名单

相比允许模型自由添加 `span.set_attribute(name,value)`，教学实现只支持固定字段：

~~~text
gen_ai.provider.name
gen_ai.request.model
gen_ai.tool.name
gen_ai.usage.input_tokens
gen_ai.usage.output_tokens
agent.task.kind
agent.workflow.phase
agent.retry.attempt
agent.verification.passed
agent.verification.reason
agent.reconciliation.state
~~~

具体字段及类型由模块内 `_safe_labels` 校验。若试图写入 `gen_ai.input.messages`、`gen_ai.tool.call.arguments`、`http.request.header.authorization`、`user.id` 或任意来源文本，将抛出 `TraceError` 而不会导出该字段。

这不代表可以无条件相信白名单字段的**值**。例如模型返回的未知 Tool Name 也可能携带密码，因此 `TracedToolRegistry` 只显示可信注册表内的 Tool Name，未知名称统一标记为 `unregistered_tool`。

### 22.7.2 有界 Span 与 Event

~~~python
tracer = TraceRecorder(
    max_spans=256,
    max_events_per_span=16,
)
~~~

默认每次 Run 最多 256 个 Span、每 Span 16 个 Event。超限时返回显式错误，不允许把未知循环产生的海量日志无限缓存在内存。

生产环境不应让普通的 Trace Collector 故障直接阻止业务运行，因此还需额外的有界队列、非阻塞导出、Dropped Telemetry 计数和失败隔离。**本章使用严格错误是为了在教学测试中清楚暴露边界，而不是推荐将遥测作为核心业务的唯一前置依赖。**

### 22.7.3 记录异常状态

原始 Exception Message 可能包含：
- URL Query Token；
- 浏览器 Cookie；
- 用户数据；
- 代码文件路径；
- Provider 的错误响应；
- 私有 Prompt/Tool Arguments。

因此本章自动异常状态只记录 `unhandled_exception` 或 `operation_cancelled` 等安全类别；显式 `SpanHandle.fail(code)` 也只能使用固定 Error Code 集合，不接受任意模型字符串。

~~~python
with tracer.span("execute_tool") as span:
    span.fail("tool_denied")
~~~

该 Span 的 `status` 变为 `error`，但其 Parent 仍可继续执行其它合法步骤。**不能因为中间一个 Tool 被拒绝，就自动把最终 Task 判定为失败。**

### 22.7.4 独立验收

~~~python
with tracer.span("verify") as verifier:
    verifier.verify(
        passed=trusted_business_verification(),
        reason="host_fixture_checked",
    )
~~~

仅在 `verify` Span 允许记录 `agent.verification.passed`。Host Verification 应读取第 10、15、16、21 章强调的独立事实，而不是直接从模型输出获取布尔值。

本章的 Record API 只能帮助遵循设计的可信 Host 约定；如果把 TraceRecorder 的 Python 对象暴露给不可信代码，仍可能伪造 Verify Span。**Trace 是观察层，不是经过数字签名的业务验收账本。**

## 22.8 费用与质量：Token Usage、Rate Card、Verified Task

### 22.8.1 Token 必须来自 Provider

第 6 章的 `GatewayResponse.usage` 可以保留 Provider 原生报告的 Input/Output/Cached Token。OTel GenAI 语义字段使用 `gen_ai.usage.input_tokens` 和 `gen_ai.usage.output_tokens`；其说明明确指出 Cached Input Token 通常已计入 Input Token Total，不能再叠加一次。[4]

本章 `record_usage` 只接受非负整数，不把字符数或近似 Tokenizer 输出假装成真实 Provider Usage。

### 22.8.2 显式 Price Card

设：
- `T_in`：Input Tokens；
- `T_out`：Output Tokens；
- `P_in`：每百万 Input Token 的美元价格；
- `P_out`：每百万 Output Token 的美元价格。

可估算：

\[
C_\mathrm{model} =
\frac{T_{\mathrm{in}}P_{\mathrm{in}}+
      T_{\mathrm{out}}P_{\mathrm{out}}}{10^6}.
\]

示例费率由可信应用显式指定：

~~~python
RateCard(
    provider="synthetic",
    model="fixture-model",
    version="fixture-2026-10",
    input_usd_per_million="1.00",
    output_usd_per_million="4.00",
)
~~~

**以上数值仅为合成教学价格，不代表任何真实模型当前报价**。真实计费还需考虑 Cache Discount、不同上下文区间、Batch、音视频、多模态、供应商政策和实际账单。

计算采用 `Decimal`，并保留 Rate Card 的 Version。历史调用应按其实际 Price/Contract Version 复核，不应静默套用当前价格。

### 22.8.3 缺失不等于零

若 Model Gateway 不提供 Usage：

~~~text
Input Tokens: UNKNOWN
Output Tokens: UNKNOWN
Estimated Cost: UNKNOWN
~~~

若有 Token，但无 Rate Card：

~~~text
Input Tokens: known
Output Tokens: known
Estimated Cost: UNKNOWN
~~~

因此本章 `TraceSummary` 对缺失 Usage 或定价的模型调用返回 `None`，而非错误地填入零。它也提供 `priced_model_calls` 和 `unpriced_model_calls`，让使用者判断费用覆盖率。

### 22.8.4 Retry 对费用的影响

第 6 章 Gateway 可自行重试。若 Gateway 只在最终 `GatewayResponse` 中报告一次 Usage，不能据此认定之前失败的 Provider Attempts 都是免费。

更完整的生产设计应把：
- 每个独立 Model Attempt；
- 自动 Retry；
- Cache Token（已经包含在 Input 总量中）；
- Streaming Partial Output；
- Provider Billed Usage；
- Price Card Version；

统一计量，避免漏算或双重计费。

### 22.8.5 Cost per Verified Task

\[
\mathrm{CostPerVerifiedTask}
=
\frac{\sum_i C_{\mathrm{all\ attempts},i}}
     {N_{\mathrm{independently\ verified}}}.
\]

分子包括成功/失败/重试导致的开销。分母来自业务 Verifier，而不是 Model API `200 OK`。如果分母为零，应显示该指标不可计算而不是 `$0`。

本章仅估算 Model Tokens 对应的部分费用；Tool API、Sandbox、GPU/CPU、网络、Browser Session、对象存储和排队成本，需要后续 Chapter 23 的完整账本。

## 22.9 真正集成 Agent Kernel 与 Model Gateway

新增：[`observability_bridge.py`](../../src/mini_agent/observability_bridge.py)。

### 22.9.1 TracedGatewayModel

它接受第 6 章 `ModelBackend.complete()` 接口，获得 `GatewayResponse` 后：

1. 校验 Provider/Model 与可信 Host 配置一致；
2. 记录 `chat` Span；
3. 只采集已知 Token Usage 和显式 Price Card；
4. 返回 `ModelReply`，供第 4 章 `AgentKernel` 正常继续控制循环。

~~~python
model = TracedGatewayModel(
    backend,
    tracer,
    provider="synthetic",
    model="fixture-model",
    rate_card=rate_card,
)
~~~

原始 Prompt/Chat Messages 必须传递给本来就有权调用的 Model Backend，但**不会被写入 TraceRecorder**。

### 22.9.2 TracedToolRegistry

~~~python
tools = TracedToolRegistry(registered_tools, tracer)
result = tools.invoke(tool_call, allow_writes=False)
~~~

它仍然调用第 4 章 `ToolRegistry.invoke` 的权限/Schema 检查，没有绕开写操作审批。对于未注册 Tool，不记录模型生成的原始 Tool Name，而使用 `unregistered_tool` 作为安全分类。

工具参数、返回内容、Stack Trace 都不进入本章 Trace。该包装器与第 19 章 Host Security Reference Monitor 是**不同的组件**：前者负责观察，后者负责安全授权。

### 22.9.3 真实接口不等于真实云调用

离线实验确实运行真实 Python Kernel、Model/Tool Wrapper 与 Verifier，但它使用受控 `FakeGateway`。因此可以证明 Span 控制流和接口兼容，不能证明某个真实大模型的 Token 价格、模型决策质量或 Provider 网络表现。

## 22.10 案例：工具被拒绝，但 Task 最终通过

可执行实验：[`examples/ch22_observability_lab.py`](../../examples/ch22_observability_lab.py)。

合成步骤：

~~~text
invoke_agent
  ├── plan (deterministic fixture, not hidden CoT)
  ├── chat #1 → proposes unregistered tool
  ├── execute_tool #1 → rejected by real ToolRegistry
  ├── chat #2 → proposes approved lookup
  ├── execute_tool #2 → handler executes once
  ├── chat #3 → final answer
  └── verify → trusted fixture checks answer and lookup count
~~~

这个例子区别了三个概念：

- **Tool Error**：第一次工具申请被拒绝；
- **Model API Success**：模型后续仍然能正常返回；
- **Task Verified**：Host 实际检查了最终结果与工具执行次数。

即使第一次工具拒绝，最后用户目标仍可能完成。反过来，多个模型调用全部成功，也不等于 Task 必然通过验收。

### 22.10.1 Canary 测试

合成 Model Tool Arguments 和 Tool Result 包含：

~~~text
SYNTHETIC_PRIVATE_CANARY_NOT_FOR_LOGS
~~~

实验在导出 JSONL 后检查 Canary 与部分 Prompt Text 没有出现在文件内。这证明该合成路径在**本章限定的字段 Allowlist** 下不泄漏这组数据，不是对所有真实文本/PII 的完整 DLP 证明。

### 22.10.2 用量与成本验算

合成三次 Model Call：

| Call | Input Tokens | Output Tokens |
| --- | ---: | ---: |
| 1 | 60 | 12 |
| 2 | 100 | 25 |
| 3 | 90 | 40 |
| **合计** | **250** | **77** |

按示例 `$1/百万 Input`、`$4/百万 Output`：

\[
C = \frac{250\cdot1+77\cdot4}{10^6}
  =\$0.000558.
\]

以上费用是明确标记的 Fixture Estimate，不是任何真实模型的实时报价。

## 22.11 Trace Playback 与 Agent Execution Replay

[`trace_store.py`](../../src/mini_agent/trace_store.py) 提供：

~~~python
write_trace_jsonl(tracer, path)
read_trace_jsonl(path)
replay_diagnostic(path)
~~~

这三个 API 的权限与含义必须讲清楚。

**Trace Playback** 只解析已记录 Span 的结构化元数据，计算 Token、费用、失败摘要和耗时，不调用任何 Model、Tool、HTTP、Shell 或数据库写操作。

**Deterministic State Replay** 根据 Run Event History 重建状态，不应该重新执行工具。

**Simulation Replay** 在隔离 Fixture/Sandbox 使用 Fake Tools 重现决策流程。

**Live Retry** 再次触达真实外部系统，需要 IAM、Approval、Effect Idempotency、Retry Budget 和状态确认。

本章只实现第一种。不能把历史 Tool Calls 重新交给真实 Gmail、付款或发布服务，就称作“无风险重放”。

## 22.12 JSONL 与哈希链的正确解释

### 22.12.1 安全 Schema

每条导出的记录包含：

~~~json
{
  "schema_version": 1,
  "sequence": 2,
  "record": {
    "operation": "execute_tool",
    "status": "error",
    "error_code": "tool_rejected_or_failed"
  },
  "previous_hash": "...",
  "entry_hash": "..."
}
~~~

这只是精简示意。真实 `record` 还含 Trace/Span IDs、时间、有限 Attributes 与安全 Events。**没有 Raw Prompt/Tool Arguments/Tool Results。**

### 22.12.2 哈希链

\[
H_i = \mathrm{SHA256}\left(
H_{i-1} \Vert \mathrm{CanonicalJSON}(R_i)\right).
\]

逐行 Reader 验证 Version、Sequence、Parent、Trace ID、Attribute Schema 和 Hash Chain。若修改一个 Error Code 而未重算后续哈希，就会检测到不一致。

### 22.12.3 哈希链不等于数字签名

具有文件写权限的攻击者可以完全重写记录并重新计算整个 Hash Chain。本章测试特意展示了这种情况。

因此本章 Hash Chain：
- 可检测部分意外修改和未经重算的改动；
- **不能**证明日志作者身份；
- **不能**证明工具在真实世界执行过；
- **不能**防止有写权限者重算；
- **不能**成为经独立审计的业务操作证据。

生产需使用有身份认证的 Append-Only Store、签名/Seal、权限、加密、Retention 和可信服务器端 Event ID。

### 22.12.4 Replay 必须失败可见

Reader 检查：
- 文件/行数大小上限；
- JSON 重复 Key、非标准常量；
- Schema Version；
- Sequence 和 Hash Chain；
- 合法 Trace/Span IDs 和唯一性；
- 已存在的 Parent Span；
- 安全事件名称/属性；
- 时间、错误类别及费用字段。

错误直接返回结构化 `TraceIntegrityError`，不悄悄丢弃被破坏的记录。

## 22.13 排查根因：Observation ≠ Explanation

`TraceSummary.primary_failure` 只是**按记录顺序找到的首个失败 Span**。它不一定是事故的实际 Root Cause。

例如：

~~~text
Model calls an unauthorized tool
    ↓
Host denies
    ↓
Model chooses authorized tool
    ↓
Host verifies task
~~~

第一个 Error 是正确的授权阻断，并不代表用户任务失败。

反例：

~~~text
Provider request timed out
    ↓
Model claims "payment failed"
    ↓
Provider may have committed
~~~

Trace 只能证明“调用方未拿到确认”，不能证明外部业务一定未发生。需要第 21 章 Operation Ledger 和 Provider Reconciliation。

因此 Root Cause Analysis 应同时检查计划版本、Tool Scope、真实服务端状态、Provider Attempt、Retry、Run Event、Sandbox Lease 和独立测试证据。最长子 Span 只能提供潜在瓶颈线索，不能自动断言“根因就是它”。

## 22.14 Trace Sampling、性能与保留

高频多 Agent 平台如果全量录制内容，可能迅速消耗存储、带宽和资源。

可考虑：
- Head Sampling；
- Tail Sampling（保留失败或高延迟 Trace）；
- Trace Buffer / Batch Export；
- 敏感数据过滤与字段大小限制；
- 每 Tenant 采样预算；
- 对关键安全审计使用独立持久化链路；
- 有明确访问权限的短时 Debug Sessions。

**业务 Run/Outbox/Operation 的持久化不允许依赖 Trace Sampling**。即使某条 Trace 被丢弃，真实副作用和状态转移仍必须由业务数据库可靠保存。

### 22.14.1 Cardinality

不要把个人邮箱、Task ID、原始 Prompt、工具参数和 URL 查询串直接当 Metric Label。指标应使用有限枚举的 Provider、Model Family、Tool Type、Operation 与 Outcome；单次 Run 的详细排查通过有权限的 Trace 关联完成。

### 22.14.2 Exporter 故障

生产 Collector 不可用时，不应该让数千个 Agent 立即阻塞在上报遥测数据的同步 I/O 上。

应将非关键 Trace Export 和业务事务隔离，使用有界队列、丢弃策略与“Telemetry Dropped”计数，而把安全审计交给具有单独可靠性契约的服务。

本章导出 `trace.jsonl` 是实验结束后的原子文件替换，不代表已实现持续的 Batch OTLP Export。
