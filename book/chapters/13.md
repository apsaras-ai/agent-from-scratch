# 第 13 章：Research Agent

> **正文初稿 v0.1，待技术审稿** · 第三篇：构建真实场景的智能 Agent  
> 本章采用**离线合成网页资料**实现一个证据驱动研究流程，不调用真实搜索引擎或 LLM。重点是建立来源完整性、结论与证据关联、冲突处理和可测试报告结构。

## 学习目标

掌握 Research Agent 的问题分解、搜索策略、证据提取、来源去重、引用、冲突识别、报告生成与评测；能够清晰区分“来源提供了这个说法”和“这个说法已经得到独立验证”。

## 13.1 Research Agent 不是“搜索 + 总结”

传统的搜索摘要可能只拼接几个网页内容。真正的 Research Agent 至少要明确：

- 用户真正需要回答的子问题；
- 哪些信息应来自一手来源；
- 每条结论引用了什么具体证据；
- 多个来源是否独立；
- 资料发布日期、适用版本是否一致；
- 冲突与未知之处是否明确暴露；
- 最终报告是否满足验证要求。

因此 Research Agent 是一个多阶段决策与证据管理系统，而不只是生成一篇漂亮的长文章。

## 13.2 系统架构

~~~mermaid
flowchart TD
 Q[Research Question] --> P[Subquestion Planner]
 P --> S[Search / Retrieval]
 S --> D[Deduplicate Sources]
 D --> E[Extract Evidence]
 E --> V[Verify Grounding]
 V --> C[Claims and Conflicts]
 C --> R[Cited Report]
 R --> A[Evaluation and Audit]
~~~

第 10 章 Planner 可分解子问题，第 7 章 Tool Runtime 可调用搜索工具，第 8 章 Context Manager 控制注入证据的量，第 9 章 Memory 可缓存带来源的历史知识，第 12 章 Durable Store 可记录长任务运行状态。**本章只提供这些模块的离线证据处理原型**，不虚构已经完成的联网集成。

## 13.3 多阶段查询规划

研究问题应该分解为能够独立检索和验证的子问题。例如“某个框架是否适合生产 Agent”可以拆为：架构、许可证、活跃维护、部署方式、可靠性机制、安全隔离和性能评测。

一个好的 Query Plan 还要标注来源优先级：官方文档和原始代码适合核对具体 API，论文可支持算法论点，社区帖子则更适合反映使用体验，但不能代替一手技术规格。

### 查询终止策略

避免 Agent 无限搜索。可以限制最大检索轮数、最大来源数、总 Token 与费用，并根据未解决的关键问题决定是否追加搜索。没有足够证据时，应该明确“不确定”，而不是填补臆测。

## 13.4 来源身份与去重

本章使用 Source ID、URL、Title、Publisher 和原始 Text 保存来源。规范化 URL 时剔除 Query 和 Fragment，以便演示相同页面的不同追踪链接去重。

这是一种**教学上简化的 URL Canonicalization**。生产中查询参数也可能决定真正不同的资源，不能无条件删除；需要遵从规范 URL、响应重定向、内容哈希与业务域的去重规则。

同一个机构镜像十次的内容不等于十个独立证据。研究可信度需要考察独立性，而非仅计算来源数量。

## 13.5 Claim–Evidence–Source 模型

~~~python
@dataclass(frozen=True)
class Evidence:
    evidence_id: str
    source_id: str
    subject: str
    predicate: str
    value: str
    quote: str

@dataclass(frozen=True)
class Claim:
    subject: str
    predicate: str
    value: str
    evidence_ids: tuple[str, ...]
~~~

对于一条 Claim，Verifier 应检查所引用的 Evidence 存在，Evidence 属于已知 Source，且引用文本确实出现在来源正文。

本章实现的验证是**引用与结构一致性检查**。它不能证明引用的作者没有错误，也不能证明文本语义一定支持 Claim：后者需要 NLI、独立检验、版本校对和人工审查。

## 13.6 冲突不应被静默消除

假设官方 Release Note 声称最低支持 Python 3.11，旧文档却写 3.10。报告不能只是选择较顺眼的数字并隐藏另一条信息。

本章 Conflict Detector 将相同 Subject + Predicate、不同 Value 的 Claim 标记为争议，附带双方来源。

真实研究系统还应考虑时间和版本：两条陈述可能分别对不同发行版成立，并不一定是真正矛盾。需要额外提取 Effective Date、版本和适用范围。

## 13.7 可审计的研究报告

[Research Agent 核心源码](../../src/mini_agent/research_agent.py) 只渲染有证据关联的 Claim，生成 Sources 区域，并列出冲突与被排除的无证据声明。

报告生成层必须把**支持来源**与**事实真伪**分开。即使两个来源一致，也不必然代表它们独立或真实；最终的高可信度研究报告应明确不确定性和验证方式。

python -m pip install -e .

python -m unittest discover -s tests -v
~~~

合成资料中有三份网页，其中两份是同一规范化 URL 的不同形式。它们对某运行时最低 Python 版本作出冲突陈述。实验展示搜索与 URL 去重、证据提取、结论过滤和冲突报告。

预期可以检查：

- 来源 URL 去重；
- Citation ID 能对应具体 Evidence；
- 无效 ID 或不匹配 Claim 被排除；
- 不同取值的冲突被报告；
- Source Quote 必须在资料正文中出现。

**所有网页 URL 和说法均为 Fixture，不是实际技术事实。**

## 13.9 评测与失败模式

Research Agent 不应只看报告是否流畅。建议至少测量：

| 指标 | 含义 |
| --- | --- |
| Citation Precision | 引用是否支持相应结论 |
| Evidence Coverage | 关键问题是否有对应证据 |
| Source Diversity | 证据来源是否独立 |
| Conflict Recall | 是否发现相互冲突的说法 |
| Factual Accuracy | 结论是否经独立核验为真 |
| Cost and Latency | 检索、模型与人工确认成本 |

典型失败模式还包括搜索结果过期、引用跳转、页面内容动态变化、摘要断章取义、网页中嵌入 Prompt Injection、模型对无证据内容编造 Citation、忽略否定条件等。

**本章只有离线结构测试，不具备真实联网研究和自动真实性鉴别能力**。生产场景应通过可靠检索工具、页面快照、出处索引、来源授权和人工抽样审查升级。

## 13.10 练习

1. 把 Research Question 拆成具有优先级的 Subquestions DAG。
2. 引入真实 Web Search Adapter，并保存抓取时间和原始页面摘要。
3. 增加文档版本与发布时间，使 Conflict Detector 区分真正矛盾和适用范围差异。
4. 实现 Claim 的引用 Precision/Recall，并制作人工标注数据。
5. 加入来源独立性、站点信誉和重复内容检查。
6. 使用第 8 章 Context Manager 限制每轮研究证据预算。
7. 使用第 12 章 Durable Store 保存检索进度和长任务恢复。
8. 设计 Prompt Injection 对抗测试，证明网页文本不应具有 Agent 执行授权。

## 13.11 总结

Research Agent 的核心不是长篇输出，而是可验证的研究过程：问题规划、来源收集、证据结构化、冲突检测、准确引用及质量评测。当前实现展示可复现的证据管理内核，后续可接入真实 LLM、搜索服务和独立 Verifier。
