# 第 11 章：Workflow 与 Agent Orchestration

> 正文初稿 v0.1，待技术审稿 · 第二篇：Agent 核心架构

## 11.1 为什么需要 Workflow？

Agent 可以动态选择动作，但许多业务步骤具有必须满足的依赖、审批和资源约束。将全部逻辑交给模型不仅难以测试，还可能在高风险操作上失去明确的控制边界。Workflow 使用由应用程序定义的状态和执行规则，Agent 只在合适节点内负责开放式任务。

## 11.2 Workflow、Agent 与 Hybrid

确定性 Workflow 的下一步由代码、图结构和规则控制；Agent 可能基于模型反馈动态生成下一步动作。两者不是互斥关系：一个 Workflow 可以包含 Research Agent 节点，一个 Agent 也可能在固定审批流程内被调用。

### 基本组件

- Node：单个任务步骤，具备 ID、依赖和 Handler。
- Edge：执行顺序和依赖。
- Run：运行状态、步骤结果和事件。
- Router：对条件结果决定哪些分支被跳过。
- Approval Gate：等待可信外部审批。
- Scheduler：选取满足依赖的节点，限制并发和预算。

## 11.3 DAG 编排

有向无环图 DAG 适合表达“先收集资料，再合并结果”的任务。设图为 G=(V,E)，只有所有前置依赖完成的节点才能进入 Ready Queue。执行器必须检测循环依赖、未知 Node ID、重复标识，否则可能无限等待。

~~~mermaid
flowchart LR
 A[Task] --> B[Inspect]
 A --> C[Search]
 B --> D[Decision]
 D --> E[Approval]
 E --> F[Write]
 C --> G[Report]
~~~

Ready Nodes 可在限额内并行执行，但有依赖或共享写资源的动作仍需串行、锁和幂等控制。当前实验将状态快照提供给并行 Handler，避免某个 Handler 在另一 Handler 执行中途读取半写入结果。

## 11.4 条件分支

条件路由可以选择执行或跳过目标节点。必须对被跳过节点的后续依赖做传播处理，否则下游 Node 会永久等待。这个问题说明为什么仅写一系列 if/else 并不能自动形成健壮的 Workflow Engine。

本章代码以 bool 作为教学路由结果，实际系统需要支持明确的路由枚举、多个分支、Join 策略、错误分支和动态插入。

## 11.5 Human-in-the-Loop

写代码、发送邮件、发布资产和删除数据不能仅凭模型声称“已经批准”执行。审批状态应包含待审批的步骤、目标资源、参数快照、审批人和有效期。本章只使用可信调用方传入的节点 ID 作为教学信号，不能视为真实的授权系统。

审批时应暂停调度；恢复时重新校验预算、身份及目标环境是否变化。长时间等待审批需要持久化和可靠调度，这属于第 12 章。

## 11.6 Python Workflow Engine 实现

[查看源码](../../src/mini_agent/workflow.py)

核心运行逻辑：

~~~python
ready = [
    node for node in pending
    if set(node.needs).issubset(results)
]
batch = ready[:max_parallel]
outcomes = await asyncio.gather(
    *(node.handler(snapshot) for node in batch),
    return_exceptions=True,
)
~~~

本章实现：

1. DAG 校验和步骤身份；
2. 并行 Ready Node 执行；
3. 条件分支和跳过传播；
4. 可信调用方的审批暂停与恢复；
5. 事件记录和步骤数量预算；
6. 节点失败时终止运行。

它是一个**内存中的教学编排器**。没有数据库、持久化队列、Worker 租约或外部副作用 exactly-once 语义。对于真正的 Agent 平台，这些能力必须由 Durable Runtime 配合提供。

~~~bash

~~~

演示的 Inspect 与 Search 可以并行，Decision 决定是否进入 Write 分支；Write 需要可信审批，Report 可独立完成。审批前 Run 为 waiting_approval，审批后完成。

测试覆盖并发峰值、无效审批、条件分支、依赖传播、非法 DAG、执行异常和预算耗尽。它们仅说明有限教学模型的行为正确，不代表真实 LLM 或生产 Worker 的可靠性。

## 11.8 与前面章节的集成

第 4 章 Agent Kernel 可以被包装为一个 Workflow Node；第 6 章 Model Gateway 负责调用模型；第 7 章 Tool Runtime 控制工具；第 8 章 Context Manager 管理节点上下文；第 9 章 Memory 提供有来源的检索数据；第 10 章 Planner 可以为确定性 Workflow 提出待审查的计划。

**核心规则：模型可以提出计划或结果，但 Workflow 的状态转移、权限和审批不能由不可信模型输出直接绕过。**

## 11.9 工程取舍

Workflow 更适合可枚举分支、高风险审批和审计流程；Agent 更适合未知路径和高变化环境；Hybrid 适合让模型在受约束的子任务里执行探索，随后回到确定性工作流进行验证。

衡量指标不只是 Task Success，也包括 p95 Latency、调用费用、重复执行、审批等待时间、失败恢复和安全事件比例。不要假定多 Agent 或更复杂的图总能带来更好效果。

## 11.10 练习

1. 增加多个条件分支和 Join（all/any）语义。
2. 实现 Node 级 Timeout、Retry 与重试退避，明确副作用幂等限制。
3. 将审批记录与参数哈希、Run ID、用户身份关联。
4. 对动态插入 Node 执行循环依赖验证。
5. 将节点事件写入第 5 章 Event Store。
6. 为不同资源设计细粒度并发锁。
7. 加入取消中间态，并处理正在执行的 Worker。
8. 对比纯 ReAct、Workflow 与 Hybrid 的任务完成率与成本。

## 11.11 总结

Workflow 负责确定性控制与约束，Agent 负责模型驱动的动态决策。可靠编排需要显式 DAG、状态、依赖、审批、并发与错误处理。当前实验尚未实现真正的持久化执行。
