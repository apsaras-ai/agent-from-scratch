# 第 26 章：Agent Benchmark 体系与可复现实验

> **状态：正文初稿 v0.1（待技术审稿）** · 第五篇：Agent Evaluation、Benchmark 与系统优化  
> 本章研究外部 Benchmark 的设计取舍、评测污染、任务覆盖、环境重置、统计与发布门，并实现离线、可复现的多领域 Benchmark 协议。**本章没有下载或运行 SWE-bench、WebArena、OSWorld、GAIA 或 BrowseComp，也没有测评真实模型。**

## 学习目标

完成本章，应当能够设计标准化 Benchmark Protocol，对 Dataset/Model/Prompt/Tool/Environment/Verifier 的版本做明确约束；按任务领域与失败原因报告结果；控制 Trial 隔离与费用归因；使用成对比较与 Regression Gate 判断是否需要阻止一次升级；理解外部排行榜数据污染风险和现实部署约束。

## 26.1 Benchmark 与一次 Eval 的区别

第 25 章的 EvalHarness 已能从公开 Task 输入开始运行真实 AgentKernel，通过可信内存环境的结果状态和工具执行轨迹判定 Outcome。Benchmark 则要求更进一步的实验规范：

- **Coverage**：任务是否覆盖预期产品的研究、编码、浏览器、工具和安全能力？
- **Protocol**：模型、Prompt、工具集、随机种子、执行环境、评分程序和预算是否可复现？
- **Comparison**：两个版本使用相同 Task/Trial/Verifier，是否报告完整回归？
- **Contamination**：基准答案或原始人工修复是否已进入训练数据？
- **Reliability**：多次运行是否稳定，还是只偶然成功？
- **Security**：隐藏答案、真实用户数据、工具权限与执行沙箱是否真正隔离？
- **Cost**：是否包含失败尝试、工具调用、环境启动和后置验收？

Leaderboard Score 是系统性实验的一种汇总，而不是对任何部署环境的终极可靠性或安全保证。

## 26.2 常见 Agent Benchmark 的定位

| Benchmark | 核心任务 | 验收依据与环境 | 适合回答的问题 |
| --- | --- | --- | --- |
| SWE-bench | GitHub Issues 与代码修复 | 仓库环境、补丁、自动化测试 | Coding Agent 能否修复真实问题 |
| WebArena | 自托管网站中的导航与操作 | 网站初始状态、环境目标与操作记录 | Web Agent 能否执行多步骤工作流 |
| OSWorld | 桌面/计算机上的多应用任务 | VM/桌面环境、配置与执行后状态 | GUI/Computer Use 能否完成开放任务 |
| GAIA | 通用多步骤研究、检索与推理 | 题目答案与资料，需按官方协议判定 | General Assistant 能否解决真实信息问题 |
| BrowseComp | 难以检索的多跳、长链网络信息 | 查询答案及浏览研究流程 | 深度浏览式 Research Agent 的检索能力 |
| τ-bench | 带工具的业务交互任务 | 模拟业务数据库最终状态与 `pass^k` | 工具 Agent 的稳定执行能力 |
| AgentDojo | Prompt Injection 和工具越权 | 合法任务与攻击目标的独立结果 | 正常能力和攻击防御的权衡 |

### 26.2.1 SWE-bench 与污染风险

官方 SWE-bench 维护多种子集，当前工具和运行命令随版本变化。评测 Patch 的正确性依赖真实仓库版本、容器环境和测试条件，不能仅根据 Diff 的语言相似度给分。[1]

**2026 年值得格外关注的更新**：OpenAI 在 2026 年公开说明停止使用 SWE-bench Verified 作为其前沿模型编码能力报告指标，指出模型在训练中接触过题目与参考 Patch 的证据，使成绩越来越受到数据暴露程度影响。[2]

这不是说所有 SWE-bench 测试都无价值，而是说**不能不分析污染风险，就把公开榜单提升当作真实软件工程泛化能力提升**。自己构造新近、可信保密、许可合规的任务集很重要。

### 26.2.2 WebArena

WebArena 是可自托管的网页操作环境，结合任务起始状态和环境验收。官方代码仓库已建议使用更完善的 AgentLab/BrowserGym 工具链做新的实验。[3]

测试时应固定浏览器版本、网站数据初始状态、登录 Session、权限、Network Policy 与 Action Schema。仅因网页显示 `Saved` 文本，不能不读服务端状态就确认任务完成。

### 26.2.3 OSWorld

OSWorld 针对桌面/GUI 工作流，原版涵盖跨应用与系统文件操作。官方 2025 年推出 OSWorld-Verified，并在 2026 年发布 OSWorld 2.0。**比较 OSWorld 排名必须说明使用的是哪一代 Dataset、Environment、Evaluator 与 Platform**，不能混合不同版本结果。[4]

执行桌面任务通常涉及 VM/Image、GUI 状态、截图、文件和应用进程。需要隔离与重置，不能让模型对真实办公账号直接执行未经许可操作。

### 26.2.4 GAIA 与 BrowseComp

GAIA 侧重现实的多步骤 Assistant 问题，常涉及查找、多模态/工具和推理。BrowseComp 聚焦难以搜索、可能需要大量网页浏览才能找到的信息。[5][6]

两者的外部信息随时间变化；评测须说明检索工具、网络日期、引用证据、答案规范化方法及是否允许人工/搜索缓存。不能在数据变化后仍当作完全相同的 Ground Truth。

## 26.3 数据污染（Contamination）比排行榜分数更重要

可能发生的情况：

1. 训练集含 Benchmark 原题或答案。
2. 某开源仓库的人工修复 Patch 进入预训练语料。
3. Agent 在检索时直接找到评测答案、Hidden Tests 或 Benchmark Discussion。
4. 研究者频繁调试 Heldout，间接把答案变为 Prompt 工程材料。
5. 自动评审模型见过公开高分响应，偏向特定表达模板。

应采取数据源检查、近重复检测、发布时间切分、全新任务采样、隔离的私有 Heldout、独立 Grader 与严格披露。

任何自建 Benchmark 都应明确：任务许可、是否来自真实用户、如何脱敏、是否已公开、谁能访问隐藏标签，以及如何防止执行环境越权。

## 26.4 设计自己的 Benchmark Protocol

本章新增 `BenchmarkProtocol`：

```python
BenchmarkProtocol(
    benchmark_id="ch25-fixture-suite",
    benchmark_version="v1",
    model_version="fake-model-v1",
    prompt_version="prompt-v1",
    tool_version="toy-tools-v1",
    environment_version="isolated-fixture-v1",
    verifier_version="outcome-grader-v1",
    isolation_profile="inprocess-not-a-sandbox",
    seed=42,
    split="heldout",
    trials_per_case=3,
)
```

这些字段有明确职责：

- Dataset 的 ID/Version 固定数据；
- Model/Prompt/Tool Version 固定 Agent 行为条件；
- Environment Version 固定初始状态和环境依赖；
- Verifier Version 固定评分条件；
- Isolation Profile 公开运行信任边界；
- Seed、Split、Trials 固定随机与统计设计。

`protocol.digest()` 对这些条件做规范 JSON 摘要。注意版本字符串是**声明**，不是远程 Provider 的签名事实；真正的运行需要可信 Artifact SHA、镜像 Digest、模型服务的版本回执和身份审计。

## 26.5 任务切片与 Macro/Micro 成绩

本章复用第 25 章 `EvalSuite` 的分类：

- Coding；
- Browser；
- Research；
- Tool；
- Security。

Micro Success：

\[
S_{\mathrm{micro}}=
\frac{\sum_d N_{\mathrm{passed},d}}
{\sum_d N_{\mathrm{trials},d}}.
\]

Macro Domain Success：

\[
S_{\mathrm{macro}}=
\frac{1}{|D|}
\sum_{d\in D}
\frac{N_{\mathrm{passed},d}}{N_{\mathrm{trials},d}}.
\]

如果 Research 有 1000 条任务而 Security 只有 20 条，总体 Micro 会更受 Research 支配；Macro 会给予每个领域相同权重。两种指标回答不同问题，不能只保留一个。

宏平均可能掩盖重要类别的内部难度变化。正式产品应按风险/重要性显式制定权重，并保留所有类别的绝对成绩和置信区间。

## 26.6 Failure Taxonomy 与 Trajectory

同样的失败率可能包含完全不同的问题：

| Failure Code | 意义 | 工程排查方向 |
| --- | --- | --- |
| `outcome_mismatch` | 最终环境没有满足目标 | Planning、Tool Choice、工具效果、Verifier |
| `policy_violation` | 存在被拒绝/未授权工具尝试 | Permission、Prompt Injection、Tool Risk |
| `runner_failure` | Agent 或 Harness 报错 | 模型/工具异常、超时、运行时 |
| `unknown_usage` | 模型费用信息缺失 | Gateway Usage、Cost Ledger、导出协议 |

第 25 章的 `ToolEvent` 只记录受控工具类型和安全原因，不复制原始 Tool Arguments/Prompt/Secret；第 26 章在此基础上统计 DomainScore 与失败计数。

如果 Agent 使用不同但合法的工具序列完成了用户目标，不能仅因为它偏离预设路径就判为失败。最终 Outcome + 安全边界是硬判据，工具冗余、复杂度和调用次数可作为软分项。

## 26.7 可复现性：哪些部分必须被冻结？

真正的 Benchmark 至少要固定：

- Task Dataset Digest 与 Ground Truth 版本；
- Run/Tool/Model/Prompt/Verifier 配置；
- Sandbox/Browser/OS/Package Image；
- Seed、Sampling Temperature 与 Retry Policy；
- Rate/Token Budget 和网络可见资源；
- Trial Reset 与缓存生命周期；
- 运行日期、Provider/工具响应可用性与外部系统版本。

本章 `assert_reproducible` 比较两次相同 Protocol+Suite 的安全摘要，验证合成运行能否完全重复。**这并不能证明真实 LLM 在相同 Seed 下必然重现完全相同的输出**；Provider 负载、路由、采样实现和环境都可能引入差异。

## 26.8 Release Regression Gate

对相同 Dataset/Protocol 的 Baseline 与 Candidate，本章 `gate_candidate` 根据以下条件决策：

1. 对照数据必须完全可比。
2. 若要求费用证据却缺失 → `insufficient_evidence`。
3. Candidate 出现任何越权 Tool Attempt → `block`。
4. 配对 Trial 的回归数超过上限 → `block`。
5. Candidate Micro Success 低于最低阈值 → `block`。
6. 满足以上条件 → `approve`（只表示离线 Benchmark Gate 通过）。

举例：

```python
decision = gate_candidate(
    baseline, candidate,
    RegressionGate(
        max_allowed_regressions=0,
        minimum_micro_rate=0.8,
        require_cost_observed=True,
    ),
)
```

**`approve` 并不是已经发布、真实生产安全认证或远程集群切流凭据。** 正式发布仍要通过第 24 章的 IAM、Canary、部署执行与业务结果读回。


比较 `baseline` 与 `candidate`，各执行两条 Heldout Case × 3 Trials。

| 指标 | Baseline | Candidate |
| --- | ---: | ---: |
| Trials | 6 | 6 |
| Passed | 3 | 5 |
| Micro Success | 50.0% | 83.3% |
| Domain Macro | 50.0% | 83.3% |
| 越权 Tool Attempt | 0 | 0 |
| 回归/改善 | 对照基准 | 改善 2 次，回归 0 |

## 26.10 真实 Benchmark 不应在普通 CI 内直接运行

SWE-bench 可能需要下载/构建大量容器，WebArena 需要自托管服务，OSWorld 需要真实桌面或虚拟机，而 GAIA/BrowseComp 涉及外部信息、浏览和许可规定。这类任务应在经过批准的专用环境中运行。

将 Pipeline 分为：

**Fast CI**：版本化的小规模 Fixture，测试 Score 函数、状态机、工具安全和报告格式，确定性且低成本。

**Real Benchmark**：固定模型/环境、专用 Sandbox、独立 Ground Truth、真实可核查的工具结果、明确成本和资源预算、统计对照与人工审查。

普通 CI 通过 15 项 Benchmark 测试只能证明**评测程序的内部不变量**，不能声称已经运行 SWE-bench 或 OSWorld。

## 26.11 统计与报告的正确口径

- `pass@k` 和 `pass^k` 同时报告，注明是“真实前 k 条观测”还是组合估计。
- Wilson 区间或 Bootstrap 必须说明 Task 独立性假设。
- 版本比较优先使用成对任务，记录改善、退化和相同。
- 任务重复 Trial 不能冒充多个互相独立的用户 Case。
- Latency/Token/Price/Cost 缺失 → Unknown，不要当成 0。
- 如果已验证任务数为零，Cost/Verified Task 不可计算。
- 预先确定 Gate Threshold，不要看完结果后只选择对 Candidate 有利的指标。

## 26.12 Benchmark 安全性和防作弊

Agent 如果能读取 Hidden Tests、直接调用 Grader、改写 Fixture 数据、伪造 Trajectory 或跳过工具授权，就可能人为提高分数。因此真正的 Benchmark 必须将：

- Dataset/Grader；
- Agent Worker/Model；
- Environment/Tool Backend；
- Telemetry/Cost Provider；

放在明确的身份/隔离边界里。

本章所有组件在同一 Python 进程中运行，`PublicTask` 不提供 Expected State 只是一条接口约定，不是防恶意代码的安全保证。将来正式 Benchmark 必须使用第 18 章 Sandbox、第 19 章 Host Policy、第 20–21 章故障恢复与第 22 章可信 Trace。

## 26.13 练习

1. 为 Benchmark Protocol 增加 Runtime Image SHA、Sampling Parameters 和 Host-approved Timeout Budget。
2. 将 Dataset 拓展到至少 50 个不同任务，标注领域、难度、Tool 契约及独立验收条件。
3. 设计一个针对 Coding Agent 的 Worktree/Testrunner Adapter，防止改动测试文件作弊。
4. 为 Browser Agent 实现环境初始化、Cookie 清理、网络/DB 后置状态验证。
5. 为 Research Agent 增加 Citation Faithfulness 和证据新鲜度检查。
6. 实现 Domain 分层 Bootstrap，避免类别内 Trial 相关性错误放大显著性。
7. 使用第 22 章 OTel Trace 报告 Tool Failure Root Cause，但不泄漏原始 Payload。
8. 对 Benchmark 添加严格的 Budget-matched Baseline，分析不同模型数量和计算预算。
9. 构造 Prompt Injection 导致越权工具尝试的反例，验证即使 Outcome 正确也会被 Gate 拒绝。
10. 设计隐藏 Case 泄漏事件处置流程，对污染任务集进行版本停用与替换。
11. 对照 OSWorld 原版/Verified/2.0 等不同版本，说明为什么不能混合发布成绩。
12. 为`SWE-bench` 的公开测试污染风险设计新近仓库、保密 Patch 和时间切分的私有评测。

## 26.14 总结

Benchmark 是**任务与环境版本约束下、可审计的端到端实验协议**，而不是将若干模型输出交给一个 Judge 后取平均分。产品应同时衡量成功、安全、成本、可靠性和失败原因；真实环境状态优先于模型自报。对外部排行榜尤其要警惕数据污染和环境版本差异。

本章实现了安全受限的离线多领域 Benchmark 与 Regression Gate，没有对任何商业模型做实际推理质量评价。

### 25–27 章技术校准（2026 年 10 月）

评测协议有两个不同层面：**共享 Evaluation Protocol**（Dataset、Tool、Environment、Verifier、Seed、Split 和 Attempts）与 **CandidateConfig**（每个候选自己的 Model、Prompt、Sampling 版本）。为了兼容旧版教学 API，`BenchmarkProtocol` 暂时保留 `model_version`、`prompt_version` 作为默认值；正式 A/B 应显式给 Baseline/Candidate 配置不同的 `CandidateConfig`，不要误以为比较双方必须使用相同模型。

`TrialContext` 将 `BenchmarkProtocol.seed` 与 Case ID、Trial Index 派生稳定的 64-bit Seed，并传给支持 `run_with_context` 的可信 Runner。旧 `run(task,env,trial_index)` 接口仍兼容，但它不消费 Seed，不能声称通过记录 Seed 就实现了真实模型随机性控制。真正生产 Runner 要把 Seed 明确传给受支持的模型采样或可控随机组件，并记录不支持确定性重放的环节。

CampaignStore 新增 **逐 Trial Checkpoint、SQLite 恢复与 Dataset Digest 核验**：每条已独立评定的 Trial 安全汇总立即保存，评测控制器异常退出后可跳过已完成 Trial。数据集改变、Campaign ID 重用、旧 Revision 或不同候选配置不能复用记录。中断中的外部副作用仍需按第 21 章进行结果核对；本章的重启恢复仅覆盖受控离线 Trial 评分记录。
