## 31.1 从 Feedback Learning 到真正的 Agentic RL（Why）

第 29 章研究**推理时搜索**：同一组参数，多尝试几条解题路径。第 30 章研究**独立验证和反馈学习**：基于已经得到的可信标签训练一个表格式决策器。

Agentic RL 又推进了一层：

> Agent 使用当前策略与环境交互 → 环境反馈改变下一步可见状态 → 收集完整轨迹 → 可信 Host 评分 → 根据回报对产生这些动作的策略分布求梯度 → 更新策略 → 用更新后的策略重新与环境交互。

与一次性回答问题最大的不同是：**动作会改变世界，世界的反馈会影响后续动作，最终结果可能在很多轮之后才能观察到。**

想象一个 Coding Agent：

~~~text
Initial task: Fix failing test
  |
  v
Agent proposes: read failing test
  |          Host validates and runs read
  v
Observation: failure message / repository state
  |
  v
Agent proposes: edit allowed source file
  |          Host approves write in isolated worktree
  v
Observation: diff and tool result
  |
  v
Agent proposes: run tests
  |          Host executes under explicit resource budget
  v
Observation: unit tests pass/fail
  |
  v
Independent verifier: regression + hidden checks + policy audit
  |
  v
Reward / quality signal → policy training → separately gated release
~~~

单一成功标记属于**整条轨迹**；选择哪些工具、何时停止、如何从失败中恢复，则发生在不同中间状态。训练需要解决“哪一步值得奖励/惩罚”的信用分配问题。

### 31.1.1 三类改进，不要混为一谈

| 机制 | 更新什么 | 需要环境交互？ | 本书位置 |
| --- | --- | --- | --- |
| Inference-time search | 当次任务的候选路径和选择 | 可选 | 第 29 章 |
| Supervised feedback / SFT | 直接拟合有标签的正确动作或输出 | 训练本身不必在线交互 | 第 30 章与本章 31.3 |
| Reinforcement learning | 通过采样路径的回报更新随机策略 | 典型 Online RL 需要反复采样 | 本章 |
| Reflection / self-improvement | Prompt、Memory、Workflow、训练数据等 | 取决于方法 | 第 32 章 |

“使用奖励模型挑最佳输出”不必然等于“用 RL 更新模型权重”；“有一个 Verifier”也不自动意味着做了 RLVR（Reinforcement Learning with Verifiable Rewards）。

### 31.1.2 为什么静态数学题 RL 与工具 Agent RL 不一样

单轮数学解题经常可以近似为：给定问题，产生整个回答，然后打一个可验证的终局分数。真实多轮 Tool Agent 则增加：

- 环境状态可能**随机、部分可观察、延迟或不一致**；
- 失败工具调用也消耗 Token、时间、配额与成本；
- 不同动作带来不同的后续 Observation；
- 一条轨迹内部可能有写文件、发邮件、审批、事务提交等不可逆副作用；
- 需要管理 Environment Reset、并行 Sandbox、数据所有权和长期依赖；
- 模型生成的工具结果或“任务已完成”文本都不能作为可信标签。

RAGEN 研究多轮交互时讨论了训练的不稳定、回报方差变化和浅层策略等问题[6]；ToolRL 专门研究工具选择与参数使用任务中的奖励设计[7]。这些结论提醒我们：**把静态回答上的 RL 配方原样套到 Agent 并不充分。**

## 31.2 将 Agent 交互形式化（Theory I）

### 31.2.1 马尔可夫决策过程

一个标准的 Markov Decision Process（MDP）可写为：

\[
\mathcal{M}=(\mathcal{S},\mathcal{A},P,r,\gamma,\rho_0).
\]

- \(\mathcal S\)：状态空间，既包含任务状态，也包含影响后续决策的环境信息；
- \(\mathcal A(s)\)：当前状态下允许的动作集合；
- \(P(s_{t+1}\mid s_t,a_t)\)：环境转移分布；
- \(r_t=r(s_t,a_t,s_{t+1})\)：即时奖励；
- \(\gamma\in[0,1]\)：折扣因子；
- \(\rho_0\)：初始状态分布。

Agent 使用参数化策略：

\[
a_t\sim\pi_\theta(\cdot\mid o_t),
\qquad
s_{t+1}\sim P(\cdot\mid s_t,a_t).
\]

这里 \(o_t\) 是 Observation。浏览器、代码仓库与真实业务系统通常不让模型直接看到完整状态，因此可用 POMDP 表示。实际策略一般依赖 Observation History、上下文摘要与外部 Memory：

\[
a_t\sim\pi_\theta(a_t\mid h_t),\quad
h_t=(o_0,a_0,\ldots,o_t).
\]

只有在历史摘要确实保留决定未来所需的信息时，才可以近似成完全观察的 MDP。

### 31.2.2 轨迹不是只有一段对话文本

一个 Episode 的显式结构可以是：

\[
\tau=(s_0,o_0,a_0,r_0,s_1,o_1,a_1,r_1,\ldots,s_T).
\]

模型/Agent 的实际执行记录还应包含：

| 字段 | 必须回答的问题 |
| --- | --- |
| task_id、dataset/split/version | 是哪个任务和哪套评测定义？ |
| policy_version、checkpoint | Rollout 由哪一版策略生成？ |
| observation、action、action mask | 这一轮看到什么，允许哪些工具？ |
| old_log_probability | 采样时该动作的概率是多少？ |
| host_tool_result、state digest | Host 实际执行了什么？ |
| terminal、truncated、failure reason | 真正完成还是预算耗尽？ |
| verifier identity、reward version | 奖励来自哪个可信来源？ |
| latency、tokens、tool calls、cost | 消耗了多少资源？ |

其中 **old_log_probability 是训练元数据，不是 Model 的自报文本**。如果真实模型通过调用工具在一次 Episode 内生成多段 Token，还需要将模型产生的 Token 与外部 Observation Token 正确对齐。

### 31.2.3 Token 不是 Environment Action

不同粒度的策略空间不能混淆：

~~~text
Token-level decision:
  select next text token (e.g. one of vocabulary IDs)

Agent-level decision:
  emit structured tool call: tool name + validated arguments

Environment transition:
  trusted host runs the approved action and produces an observation
~~~

真实 LLM Training 经常对生成 Token 的 Log Probability 求梯度，同时把许多 Token 组合成一次工具调用；外部工具响应、系统消息、用户消息不应随意当作模型采样的动作 Token 去计算策略梯度。

工具参数、Action Mask、Token Mask、Turn Mask、Stop Action 和 Truncation 一旦处理错误，可能造成看似“训练成功”的虚假指标。

### 31.2.4 目标函数与稀疏奖励

RL 的典型目标是最大化期望折扣回报：

\[
J(\theta)=\mathbb E_{\tau\sim p_\theta(\tau)}
\left[R(\tau)\right],
\qquad
R(\tau)=\sum_{t=0}^{T-1}\gamma^t r_t.
\]

当只有终局奖励时：

\[
r_t=0\quad (t<T-1),\qquad
r_{T-1}=\mathbf{1}[\text{Host verifies success}].
\]

这个形式容易定义，但难优化：数十次工具调用之后才收到一个二元分数。可以设计过程奖励（例如确认测试通过、找到相关证据），但必须先验证过程指标与最终任务成功正相关，且不能鼓励多余调用、伪造证据、绕过测试或逃避审批。

**不可逆工具操作不能为了探索而在真实用户环境中随意重复。** 训练应优先采用可重置的可信 Fixture、快照化 Sandbox 和外部副作用模拟。

## 31.3 SFT、DPO 与 RL 分别解决什么问题（Theory II）

### 31.3.1 SFT：模仿已有正确轨迹

给定专家动作序列 \((h_t,a_t^*)\)，监督微调可以最小化：

\[
\mathcal L_{\mathrm{SFT}}
=-\sum_{(h_t,a_t^*)\in D}\log \pi_\theta(a_t^*\mid h_t).
\]

这是**模仿数据**，而不是最大化模型自己探索得到的回报。SFT 适合训练可靠 Tool Call JSON、工具参数语法、错误恢复示范、既定操作规范等。

局限包括：只能直接学习数据覆盖的行为，错误历史带来的 Distribution Shift，以及长路径标注成本。

### 31.3.2 DPO：直接利用偏好对

对于同一个条件 \(x\)，给定偏好输出 \(y_w\) 和非偏好输出 \(y_l\)，DPO 在特定 KL 约束偏好建模下优化[3]：

\[
\begin{aligned}
\mathcal L_{\mathrm{DPO}}
=-\mathbb E_{(x,y_w,y_l)\sim D}
\log\sigma\Bigg(
\beta \Big[
&\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\mathrm{ref}}(y_w\mid x)}
\\[-2pt]
-&\log\frac{\pi_\theta(y_l\mid x)}{\pi_{\mathrm{ref}}(y_l\mid x)}
\Big]\Bigg).
\end{aligned}
\]

DPO 的优势是训练时不必搭建完整的在线 Rollout + Reward Model + PPO 训练环，但**它不等价于在动态环境中做在线策略梯度**。对于 Tool Agent 的偏好数据，还需确保成对轨迹在任务、环境起点、可用工具和约束上可比较。

本章代码**不实现 DPO**，只对概念、数据要求与 RL 的选择标准做区分。

### 31.3.3 如何做方法选择

| 已有条件 | 优先尝试 |
| --- | --- |
| 完整正确轨迹、可靠专家标签 | SFT |
| 同任务的优劣输出对、没有便宜的环境回报 | DPO / Preference Optimization |
| 可重复调用的可信工具环境、可验证终局、可承受探索成本 | Online RL / RLVR |
| 环境不可重置、操作有真实副作用 | 改 Runtime/Guardrail、做离线 Evals，谨慎评估离线学习 |
| Reward 不可靠、上线质量门不完善 | 先修第 25–30 章评测与 Verifier，而不是先扩大 RL 算力 |

SFT、DPO、RL 可以成为多阶段训练流水线的组成部分，不需要将其视为互相排斥的“路线之争”。DeepSeek-R1 的公开说明与 Nature 论文区分了使用 RL 激励推理行为和多阶段训练的不同作用[5]。

## 31.4 从 REINFORCE 推导策略梯度（Theory III）

### 31.4.1 为什么可对采样概率求导

如果环境转移不依赖策略参数，轨迹概率可分解为：

\[
p_\theta(\tau)
=\rho_0(s_0)\prod_t
\pi_\theta(a_t\mid h_t)
P(s_{t+1}\mid s_t,a_t).
\]

利用 Log-Derivative Trick：

\[
\begin{aligned}
\nabla_\theta J(\theta)
&=\nabla_\theta\int p_\theta(\tau)R(\tau)d\tau\\
&=\mathbb E_{\tau\sim p_\theta}
\big[R(\tau)\nabla_\theta\log p_\theta(\tau)\big]\\
&=\mathbb E_{\tau\sim p_\theta}
\left[R(\tau)\sum_t\nabla_\theta\log\pi_\theta(a_t\mid h_t)\right].
\end{aligned}
\]

环境转移本身不需要可微，这是 Agentic RL 能接入数据库、浏览器和代码工具的关键之一。

实际 REINFORCE 常使用 Return-to-go \(G_t\) 并减去不依赖当前采样动作的 Baseline \(b(h_t)\)：

\[
\nabla_\theta J(\theta)
\approx\frac{1}{N}\sum_{i=1}^{N}\sum_t
\big(G_{i,t}-b(h_{i,t})\big)
\nabla_\theta\log\pi_\theta(a_{i,t}\mid h_{i,t}).
\]

其中 \(A_t=G_t-V(h_t)\) 被称为 Advantage 的一种常见构造。

本章的教学环境只在 Episode 末尾返回二元奖励，令 \(\gamma=1\)，因此每一步拿到同一个 Terminal Return。**这不是精细 Credit Assignment**：它无法告诉我们两步中哪一步贡献了成功，只能通过随机试错把奖励相关的路径概率逐渐提高。

### 31.4.2 表格式 Softmax 的梯度

我们不用 Transformer，而使用一组对不同 Observation 存储的 Logits：

\[
\pi_\theta(a\mid o)
=\frac{\exp z_{o,a}}{\sum_{b\in\mathcal A(o)}\exp z_{o,b}}.
\]

求导得到：

\[
\frac{\partial\log\pi_\theta(a\mid o)}
{\partial z_{o,k}}
=\mathbf 1[k=a]-\pi_\theta(k\mid o).
\]

因此一次优势为正的采样，会提高采样动作相对其他动作的 Logit；优势为负，则相反。实际实现还需：

- 只对合法动作归一化 Softmax；
- 拒绝 NaN、Inf、Bool 伪装的数值及超预算任务；
- 用 Frozen Policy 产生本批数据；
- 用独立 Host Verifier 验证整个 Episode；
- 正确记录采样、更新和评测的独立随机种子。

### 31.4.3 Baseline 与方差

朴素 REINFORCE 在稀疏奖励任务中方差很大。加入不依赖当前动作的 Baseline 可以降低方差；实际可以使用过去 Batch 的滑动均值、Leave-one-out Baseline，或学习 \(V_\phi(h)\) 的 Critic。

本章代码为了足够小，使用同一批轨迹的 Reward 均值进行中心化，作为**有有限样本偏差的教学近似**（共享 Batch 均值会让样本与自身 Baseline 相关）。不要误称它为完整 Actor–Critic、GAE 或无偏梯度估计。

## 31.5 PPO：为什么要限制每次策略更新（Theory IV）

假设 Batch 由固定的旧策略 \(\pi_{\mathrm{old}}\) 采样。更新过程中策略变为 \(\pi_\theta\)，一个动作的概率比率为：

\[
\rho_t(\theta)=
\frac{\pi_\theta(a_t\mid h_t)}
{\pi_{\mathrm{old}}(a_t\mid h_t)}.
\]

PPO-Clip 的基本目标[1]是：

\[
L^{\mathrm{CLIP}}(\theta)
=\mathbb E_t\left[
\min\left(
\rho_t\hat A_t,\;
\operatorname{clip}(\rho_t,1-\epsilon,1+\epsilon)\hat A_t
\right)\right].
\]

请特别注意正、负 Advantage 的不对称：

| 样本 | 情况 | 梯度直觉 |
| --- | --- | --- |
| \(\hat A>0\) | 动作概率被提高，且 \(\rho>1+\epsilon\) | 不再从这个样本继续奖励上涨 |
| \(\hat A<0\) | 动作概率被压低，且 \(\rho<1-\epsilon\) | 不再从这个样本继续鼓励下降 |
| \(\hat A<0\) | \(\rho>1+\epsilon\) | 仍可惩罚过度提高的坏动作 |
| \(\hat A>0\) | \(\rho<1-\epsilon\) | 仍可鼓励被过度压低的好动作 |

例如 \(\epsilon=0.2\)，正优势样本 \(\rho=1.5\) 的裁剪替代目标被限制在 \(1.2\hat A\)，在该区间的奖励项梯度为零。但**PPO 裁剪不保证绝对 KL 距离上界**；真正的生产实现仍需考虑 KL Monitor、Early Stop、Optimizer、Gradient Clipping、Reference Policy 与数值稳定性。

本章 PPO-style 实验具备：

1. 每次采样前冻结旧策略；
2. 同一 Batch 进行多轮 clipped surrogate 更新；
3. 每个合法 Tool Action 计算离散 Softmax 的精确 Log Probability；
4. 可选相对于固定 Reference 的精确 Categorical KL 正则；
5. 使用**终局奖励减 Batch Mean**作为 Advantage。

它**不具备**学习 Value Network、GAE、分布式 Minibatch、Transformer Token Mask 和成熟 PPO 框架的所有配套功能。别把“小实验用到了 PPO 裁剪函数”写成“完整复现 PPO 训练系统”。

## 31.6 GRPO：不训练 Critic，怎样估计优势？（Theory V）

DeepSeekMath 提出 Group Relative Policy Optimization（GRPO），使用同一问题采样多个候选的组内 Reward，计算相对 Advantage，从而避免独立训练一个同规模 Critic 的开销[4]。DeepSeek-R1 的 RL 研究也采用了 GRPO 思路[5]。

对于同一个问题 \(q\) 的 \(G\) 条轨迹 \(\tau_1,\ldots,\tau_G\)，设各自可信终局得分为 \(R_i\)，则：

\[
\bar R=\frac1G\sum_{i=1}^G R_i,\qquad
\sigma_R=\sqrt{\frac1G\sum_{i=1}^G(R_i-\bar R)^2},
\]

\[
\hat A_i=
\begin{cases}
(R_i-\bar R)/\sigma_R,&\sigma_R>0,\\
0,&\sigma_R=0.
\end{cases}
\]

GRPO 在 PPO-style 的概率比率、裁剪目标之外通常还加入相对于 Reference Policy 的 KL 控制。对 Agent 的简化教学目标可写为：

\[
J_{\text{toy}}
=\frac1G\sum_{i=1}^G\frac1{T_i}\sum_t
\min\left(\rho_{i,t}\hat A_i,
\operatorname{clip}(\rho_{i,t},1-\epsilon,1+\epsilon)\hat A_i\right)
-\beta D_{\mathrm{KL}}(\pi_\theta\Vert\pi_{\mathrm{ref}}).
\]

这是解释用的**工具动作级教学式**，不等价于 DeepSeekMath 的完整 Token-level 目标：真实工作流还涉及 Token Normalization、Mask、不同长度轨迹的权重和 KL 估计器选择。

### 31.6.1 算一个最小的 Group Advantage

若同一任务抽到四条轨迹，真实奖励为：

\[
R=(1,0,0,1),\quad
\bar R=0.5,\quad
\sigma_R=0.5,
\]

则：

\[
\hat A=(1,-1,-1,1).
\]

成功路径上的每个已采样动作获得正优势；失败路径上的每个动作获得负优势。相比绝对分数，中心化会改变优化信号的尺度。

**危险边界**：如果一组 \(G\) 条样本全部失败，或者全部成功，就有 \(\sigma_R=0\)，组内没有相对排序信号。本章将其明确设为零，不添加虚假梯度。这不表示所有实现都不能增加别的辅助 Loss，而是**终局 Reward 项本身已经没有区分力**。

### 31.6.2 为什么 Group Size 和任务难度重要

若成功概率极低，所有轨迹都失败的概率很高；若成功概率接近 1，所有轨迹都成功也很常见。前者缺少积极样本，后者可能不再提供显著学习信号。

因此真实训练常需要设计难度 Curriculum、初始状态多样性、Reward Shaping 和有效的 Group Sampling。但“调整任务让 Reward 更容易区分”不能越过可信测试，不能让模型通过调用额外工具或伪造环境状态作弊。

### 31.6.3 PPO/GRPO 不直接解决跨轮 Credit Assignment

把一条轨迹的相同 \(\hat A_i\) 分配给其中每个动作，是一个简单的 Trajectory-Level 信用分配近似：

\[
\hat A_{i,t}:=\hat A_i.
\]

在长流程中，单个错误可能发生在第 2 步，后面 20 步只是重复输出。这时统一回传终局分数可能效率低、噪声大。可能的改进包括：

- 可信的过程级辅助反馈；
- Actor–Critic / GAE / TD 等价值估计；
- 以 Tool Turn 或 Subtask 切分轨迹的 Hierarchical Credit Assignment；
- 对已验证分支做 Backtracking 或更有针对性的 Rollout；
- 给失败原因打标，但不让模型自报结果替代环境事实。

RAGEN 的 StarPO/StarPO-S 与 Agent Lightning 的层级 credit assignment 都是进一步阅读的研究方向[6][8]。

## 31.7 真实 Agentic RL 系统如何组织（Design）

### 31.7.1 推荐拆分：Rollout 系统与 Learner 解耦

~~~mermaid
flowchart TD
    Task[Versioned task sampler] --> Actor[Agent actor / frozen policy version]
    Actor --> Host[Host authorization and budgets]
    Host --> Env[Resettable isolated environment]
    Env --> Obs[Trusted observations / tool result]
    Obs --> Actor
    Actor --> Trace[Trajectory store and token/action masks]
    Env --> Verifier[Independent process and outcome verifier]
    Trace --> QC[Trace integrity / eligibility checks]
    Verifier --> QC
    QC --> Buffer[On-policy training batch]
    Buffer --> Learner[PPO / GRPO learner]
    Learner --> CKPT[Checkpoint + policy version]
    CKPT --> Eval[Independent heldout eval / safety gate]
    Eval -->|approved| Actor
~~~

这张图的核心是 **Control/Execution/Training 三层分离**。训练时的 Reward Reader 不能被 Agent 直接写入；评测用的隐蔽答案不能在 Prompt 或可查询工具接口中泄漏。

Agent Lightning 提出训练与 Agent 执行解耦的思路，并设计轨迹到训练转移的抽象[8]；verl 的 Agentic RL 文档讨论多轮 Tool Rollout、服务化异步 Rollout 等工程问题[9]。这些框架提供了有价值的系统组织思路，但配置一个框架不等于验证了奖励来源、安全隔离或生产部署质量。

### 31.7.2 必须专门处理的系统问题

| 系统问题 | 建议约束 |
| --- | --- |
| Policy Staleness | 记录 sampling policy version；评估延迟 Rollout 的比率和有效性，不盲目当 On-policy 数据 |
| Environment Reset | 为每个 Episode 创建独立起点、独立 Workspace/会话与稳定工具 Fixture |
| Deterministic/irreversible effects | 支付、发布、邮件、真实写操作不参与未经授权的 RL 探索 |
| Reward provenance | 记录 Dataset、Verifier、Reward 版本及可信执行回执，独立审计 |
| Replay / tool budget | 失败调用也计费；不允许超预算后把日志裁剪成“成功路径” |
| Context / action masking | 只对策略生成的合法 Action/Token 求梯度，不对外部观察计算策略概率 |
| Length / stopping bias | 比较短路径和长路径；测 Stop、Truncation、超时及重复工具调用 |
| Data leakage | 隐藏答案、Heldout、Benchmark 实现细节不可进入训练上下文 |
| Monitoring / rollback | 同时检查 verified task success、policy violations、latency、cost 和 regression slices |

第 18–21 章的安全隔离、审批、并发租约和故障恢复，在 Agentic RL 期间**仍然适用**。训练时调用工具不是安全规则的例外。

### 31.7.3 如何构造 Reward，如何避免 Reward Hacking

可以将 Reward 与硬约束分别定义：

\[
R(\tau)
=R_{\mathrm{verified\ outcome}}(\tau)
-\lambda_c C(\tau)-\lambda_\ell L(\tau),
\]

并额外要求：

\[
\text{ToolPolicyViolations}=0,
\quad \text{UnauthorizedEffects}=0,
\quad \text{ReleaseGatePassed}=\text{true}.
\]

式中的 Cost/Latency 权重只在拥有可信计量、明确业务目标时才应使用。对于未通过权限检查、伪造结果和无法核实的副作用，更稳妥的方法通常是**硬拒绝/安全门**，而不是让一个可学习的 Reward Score“抵消”风险。

第 30 章的 Reward Hacking 实验说明：错误代理 Reward 会系统性奖励错误路径。RL 会把这一问题放大，因为它会主动找到奖励函数的可利用漏洞。DeepSeek-R1 的公开论文也讨论过基于模型的奖励带来的 Reward Hacking 现象[5]。

## 31.8 从零实现：最小多轮算术 Agent RL（Implementation）

### 31.8.1 为什么选择算术工具，而不是立即训练 LLM

要理解 RL，首先需要证明：

1. 随机策略真的提出工具动作；
2. Host 在每轮真实更新环境状态；
3. 下一次采样取决于新 Observation；
4. 终局 Verifier 真正依据已执行轨迹给分；
5. 训练结果真的修改了 Policy Logits；
6. 更新后的策略确实在**独立重新采样**下得到更高成功概率。

把在线 LLM、GPU、网络和不可信代码同时加入第一个实验，会让失败原因变得难以定位。本章因此构造**可枚举状态空间、只有 3 种安全操作、2 个决策步骤**的环境：

~~~text
Task: initial=1, target=8, horizon=2

Allowed actions:
  add1: x -> x + 1
  add3: x -> x + 3
  mul2: x -> 2 * x

Successful path:
  1 --add3--> 4 --mul2--> 8

Terminal verifier:
  final == target => reward=1.0
  else            => reward=0.0
~~~

在初始状态上三个动作等概率，各后继状态的三个动作也等概率；只有一条二步路径能成功，因此随机策略的**精确**成功概率是：

\[
P_{\text{uniform}}(\text{success})=\frac13\times\frac13=\frac19
\approx11.11\%.
\]

注意，这是特定合成环境的数学真值，不是 Benchmark 统计结论。

### 31.8.2 代码结构

| 文件 | 作用 |
| --- | --- |
| [agentic_rl.py](../../src/mini_agent/agentic_rl.py) | 安全算术 Transition、Trajectory/Verifier、Softmax Policy、REINFORCE/PPO/GRPO 的真实参数更新 |
| [ch31_agentic_rl_lab.py](../../examples/ch31_agentic_rl_lab.py) | 用相同任务和种子跑三个训练模式，并以新 Rollout 评测 |
| [test_ch31.py](../../tests/test_ch31.py) | 轨迹真实性、动作权限、概率归一化、裁剪梯度、零方差、KL 与训练收敛性检查 |
| [ch31_rl_review.md](../../docs/ch31_rl_review.md) | 从教学实验走向真实 Agentic RL 的审核清单 |

关键调用示意：

~~~python
from mini_agent.agentic_rl import (
    ArithmeticTask, TabularPolicy, TrainingConfig,
    train_policy, exact_success_probability,
)

task = ArithmeticTask("reach-eight", 1, 8, 2)
baseline = exact_success_probability(TabularPolicy(), task)

policy, reports = train_policy(
    task,
    TrainingConfig(
        mode="grpo",
        batch_size=32,
        group_size=8,
        learning_rate=2.0,
        epochs=4,
        clip_epsilon=0.2,
        kl_beta=0.01,
    ),
    rounds=140,
    seed=31,
)

learned = exact_success_probability(policy, task)
print("baseline:", baseline, "after:", learned)
~~~

真实实现中，每轮先复制 Frozen Old Policy，通过旧策略收集 Batch，再用固定 Old Probability 计算新旧 Policy Ratio。**不允许在采样到一半时悄悄更新旧策略**，否则重要性比率就不再表示采样分布变化。

### 31.8.3 独立 Host Replay 的重要性

工具动作本身只能是三个固定字符串，且受 Host Allowlist/数值边界约束。Verifier **从可信初始状态完整重放**，不接受策略提交的“最终状态”或“我已成功”文本。

单元测试专门证明这些情况会被拒绝：

- 把 Tool 返回的 4 篡改成 8；
- 把失败 Episode 的 Reward 改成 1；
- 使用不存在或越界的工具；
- 提交缺少最后一步的轨迹；
- 将 Bool、NaN、Inf 等无效值冒充数字；
- 在不存在回报差异的 GRPO Group 中凭空产生学习信号。

这些检查只覆盖固定 DSL，不构成现实 OS、Browser 或 Network 的安全沙箱。

### 31.8.4 三个算法实际执行了什么

- **REINFORCE**：一批 On-policy 轨迹，一轮 Score Function 梯度更新，使用 Batch-centered Return；
- **PPO-style**：相同 On-policy 数据，多轮使用 Frozen Old Policy 的 Clipped Surrogate 更新；
- **GRPO-style**：每个 Group 从同一任务状态独立抽样，组内归一化 Terminal Rewards，再通过相同的 Clipped Surrogate 更新；
- **KL**：可选对已访问状态的有限 Categorical Distribution 计算精确 \(D_{\mathrm{KL}}(\pi_\theta\Vert\pi_{\mathrm{ref}})\) 梯度，固定 Reference 不随训练改写。

本章的 KL 与 PPO/GRPO 目标仅在**有限动作空间**上计算，不是深度语言模型中的 Token-level 采样 KL Estimator，也没有预训练语言能力需要保护。用于教学很合适，但不能把它称为“以 DeepSeekMath 相同代码训练 LLM”。

## 31.9 实验、指标与反证（Evaluation）

### 31.9.1 一键运行

在仓库根目录、Python 3.11+ 环境中：

~~~bash
python -m pip install -e .
python examples/ch31_agentic_rl_lab.py
python -m unittest discover -s tests -p 'test_ch31.py' -v
~~~

不需要 GPU、真实模型 Key、网络工具或运行不可信代码。

实验会显示：

- **训练前精确成功概率**：初始固定环境为 \(1/9\)；
- **训练后精确成功概率**：枚举有限 MDP 的全部合法路径计算，并非抽样估计；
- **新种子 Rollout 成功数**：独立重复交互验证；
- **学习数据量**：累计采样了多少条 Episode；
- **裁剪项计数**、**GRPO 零方差 Group 计数**；
- **未见目标的测试结果**：强调表格式策略没有跨目标自动泛化。

**不要把固定种子的一次实验推广为算法优劣排名。** 真正比较 REINFORCE、PPO 与 GRPO，需要多个 Seeds、匹配相同的 Environment Step/Verifier 预算、固定网络容量、超参数搜索预算及不相交测试任务，并报告置信区间和真实 Cost。

### 31.9.2 设计自己的对照实验

建议依次做六组 Ablation：

| 对照 | 操作 | 应关注 |
| --- | --- | --- |
| Uniform Baseline | 不训练 | 精确成功率应为 \(1/9\) |
| REINFORCE vs PPO vs GRPO | 固定环境与采样预算 | Reward、方差、梯度与训练成本 |
| Group Size | 2、4、8、16 | 零方差组比例与收敛 |
| Clip Epsilon | 0.05、0.2、0.4 | 被裁剪比例、策略移动幅度与学习稳定性 |
| KL Beta | 0、0.01、0.1 | 与初始策略的距离、探索与收敛速度 |
| Reward Abstraction | Terminal-only vs 经审计的过程奖励 | Reward Hacking 与终局成功是否背离 |

对于本章的表格式策略，换了 Target 通常就换了一个全新的 Observation Key。因此“新 Seed 上成功率提高”只能证明**同一任务分布下的策略优化**，不能证明对未知 Goal 的泛化。这正是设计真实 Agent Benchmark 时必须特别小心的地方。

### 31.9.3 从实验正确性到研究结论，中间还差什么

当前结果最多能支持：

> 在固定二步合成算术工具环境中，给定可信二元终局 Reward，Policy-gradient 类更新可以改变策略参数并提高由独立 Verifier 定义的任务成功概率。

不能支持：

- 某个现实 LLM 已经掌握了 Agentic RL；
- PPO/GRPO 在生产 Coding、Browser、Research Agent 上一定优于 SFT；
- 一条可信合成轨迹具有真实系统的安全性；
- 表格式策略对新任务、新工具、新领域有泛化；
- Unit Tests 已证明完整 PPO 算法、训练无偏、收敛最优或生产隔离有效。

此外，任何外部 Provider 的模型训练都应另行核实数据条款、训练权限、推理费用、对话内容可见性和日志留存范围。

## 31.10 学完这一章之后怎么继续

后续第 32 章将引入 Self-Improving Agent：不只更新某个 Policy，而是研究 Prompt、Memory、Workflow、Tool Strategy 与训练数据如何在长期任务中自我改进。

但是**闭环自改进不等于无门槛自动上线**。安全的自改进至少要保证：

1. **可靠的事实源**：可信工具结果与外部验证；
2. **可追溯的候选改变**：Prompt/Policy/Workflow/Dataset/Reward Version；
3. **独立测试集**：训练与评测解耦；
4. **明确的安全门槛**：有无权限违规与不可逆副作用；
5. **可停止、可回滚**：失败时恢复前一可信版本。

这也是本书从 Agent Kernel、Tool System、Sandbox、Observability、Evaluation 一直铺垫到 Agentic RL 的原因。

## 思考题与动手练习

1. **推导**：从 \(\nabla_\theta\mathbb E[R]\) 出发证明 Score Function Identity；什么条件下可以从 Log Probability 中消去环境转移项？
2. **数值题**：同一 Group 的 Reward 是 \((1,0,0,0)\)。算出 GRPO Advantage；若四条全部失败会怎样？
3. **PPO 细节**：\(\epsilon=0.2\) 时，分别计算 \((\rho,A)=(1.4,1), (0.5,-1), (1.4,-1)\) 的 Clipped Surrogate 和梯度分支。
4. **代码题**：把 Batch-centering 改成 Leave-one-out Baseline；分析估计偏差和有限样本方差的变化，增加回归测试。
5. **代码题**：把终止条件从固定两步改成显式 Stop Action；添加合法提前成功、错误过早停止和超预算 Truncation 的测试。
6. **系统设计**：设计一个隔离 Coding Agent 的 Resettable Environment，说明在并行 Rollout 时如何防止候选 Patch、测试缓存或共享 Secret 互相污染。
7. **奖励设计**：提出两个会导致工具滥用的错误 Proxy Reward，并给出 Host 独立验证和 Metric Gate。
8. **研究题**：将 RAGEN、ToolRL、Agent Lightning 中的训练样本单位、Reward 粒度与执行/训练架构画成一张对照表。
9. **反证练习**：设计一个新 Target 测试，证明本章表格式策略即便在训练任务上成功率接近 1，也不能自动推断对未知目标的泛化。
