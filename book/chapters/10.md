# 第 10 章：Reasoning、Planning 与 Verification

> **状态：正文初稿 v0.1（待技术审稿）** · 第二篇：Agent 核心架构  
> 实验为 Python 标准库实现的**确定性规划与验证闭环**，不宣称具备真实 LLM 的推理能力，也不运行真实代码仓库。

## 学习目标

理解 ReAct 与 Plan-and-Execute 的适用条件；将任务拆为带依赖关系的 DAG；观察动作反馈并动态重规划；明确区分模型声明、工具报告和独立任务验证；实现停止条件、预算和失败记录。

## 10.1 为什么 Agent 需要 Planning？

Tool Calling 只能回答“这一刻请求哪个动作”。复杂任务还要解决长程目标、顺序依赖、失败恢复和何时结束的问题。

例如修复仓库测试必须经历：定位失败 → 修改代码 → 再次运行测试 → 检查结果。模型输出“修复已完成”不等于环境实际通过测试。

规划不是产生一个好看的 TODO 列表，而是给执行器一个可以检查和修订的动作结构。

## 10.2 ReAct 与 Plan-and-Execute

**ReAct** 在每次观察后选择下一步动作，优势是快速适应未知环境；缺点是长任务容易重复探索、丢失目标或增加模型调用。

**Plan-and-Execute** 先形成明确的任务计划，再逐步执行并检查。优点是方便追踪依赖关系和预算；缺点是初始计划可能建立在错误环境假设上。

实际工程通常采用混合结构：

~~~mermaid
flowchart TD
    G[Task Goal] --> P[Plan]
    P --> E[Execute ready step]
    E --> O[Observation]
    O --> V{Verified?}
    V -->|No / changed environment| R[Replan]
    R --> P
    V -->|Yes| F[Finish]
~~~

注意这里的 ReAct 是一种交互式策略模式；本章离线代码使用明确规则重规划，**不是在运行模型的内部 Chain-of-Thought**。

## 10.3 将任务表达为 DAG

定义计划：

[
P=(V,E)
]

其中 (V) 是步骤集合，(E) 是依赖边。当步骤 (u) 必须在步骤 (v) 之前成功执行时，存在边 (u\rightarrow v)。

每个步骤包含 step_id、action、dependencies。执行器只能选择其所有依赖已完成的步骤。

~~~python
@dataclass(frozen=True)
class PlanStep:
    step_id: str
    action: str
    dependencies: tuple[str, ...] = ()
~~~

本书用 DFS 检测依赖环、未知依赖和重复 ID。真实系统还应考虑资源锁、审批状态、重试与动态子任务。

## 10.4 状态机与执行反馈

步骤最少包含 Planned、Running、Succeeded、Failed 等状态。执行后应记录真实 Observation，而不只是记录模型的文字解释。

| 状态/结果 | 应执行的控制逻辑 |
| --- | --- |
| 步骤成功 | 标记完成，使依赖它的步骤进入可执行候选 |
| 工具失败 | 请求修订或停止 |
| 依赖尚未完成 | 不执行 |
| 计划发生环 | 在执行前拒绝 |
| 预算耗尽 | 以明确原因停止 |
| 全部步骤完成 | 进入独立验收，而非直接报告成功 |

第 5 章的 Run/Event 模型适合保存这些变化；本章用轻量内存状态演示算法。

## 10.5 计划修订与已完成步骤保护

环境可能与计划不符。例如先执行测试发现 FAIL，Planner 决定增加“检查”和“修复”，然后再测试：

~~~text
Initial: test
           |
           +-- FAIL
                |
                v
Replan: inspect -> patch -> test
~~~

一个关键不变量：新计划**不能默默重新定义一个已经完成的步骤**，否则历史记录中“已完成”的含义会发生漂移。本章校验已完成步骤在新计划中的动作和依赖保持不变。

在生产系统中，修改已完成步骤的目标可能确实有必要，但需要创建新 Step ID、增加显式废弃事件或新 Run，而不是修改旧历史。

## 10.6 Reflection 与 Self-Correction

Reflection 不一定要修改模型权重。推理时的自我修正通常根据反馈重新形成问题假设或行动计划。

例子：初始假设是依赖错误，真实测试反馈则指向逻辑错误。正确的修正依据应包括测试日志、代码差异、可执行验证等外部证据。仅让同一模型再说一遍“我想对了没有”，不能保证错误减少。

区分三个层次：

1. **Self-Review**：同一模型检查文本或方案；
2. **Tool Feedback**：编译器、测试、查询或搜索产生外部观察；
3. **Independent Verifier**：根据事先定义的验收标准检查真实状态。

本书优先通过第 2 和第 3 层建立可靠反馈闭环。

## 10.7 Verifier：何时才算完成？

一个好的 Verifier 不应仅相信模型声称“已完成”。它应检查可观察的任务后置条件。

本章模拟仓库环境：代码状态必须不再 broken，并且测试必须通过。即使执行了 claim_success 动作，也不能直接满足验收。

~~~python
def verify(self) -> CheckResult:
    passed = not self.broken and self.test_passed
    return CheckResult(
        passed,
        "verified_repository_and_test" if passed
        else "repository_or_test_not_verified",
    )
~~~

这个 Verifier 是独立于模拟工作器声明的确定性检查，但不是生产级 Verifier。真实 Coding Agent 需要工作树状态、编译、单元测试、隐藏测试、权限和补丁审查等更多证据。

## 10.8 停止条件和循环保护

一个会自主修改计划的 Agent 如果没有边界，可能进入“失败 → 重新规划 → 再失败”的无限循环。本章使用 max_actions 强制限制。

实际系统还应独立限制模型调用次数、工具调用次数、Token、费用、执行时限、重复状态与人工审批。一个完成的计划 DAG 不等于任务成功，必须经过 Verifier。

## 10.10 如何评估规划系统？

至少记录：

- Task Success Rate：经独立 Verifier 的成功占比；
- Plan Validity：有效 DAG 比例；
- Replan Count：每次任务修改计划的次数；
- Step Failure Rate：工具执行失败比例；
- Budget Exhaustion Rate：因成本或步骤上限停止的比例；
- Cost per Successful Task：整个任务成本除以成功任务数。

还应固定任务集、环境版本和模型参数，对比纯 ReAct、静态 Plan-and-Execute、允许 Replan 的混合架构。计划越长不意味着质量越高；额外规划模型调用可能反而增加成本和错误。

## 10.11 安全与可靠性边界

本章实验没有真实文件写入、Sandbox 或外部工具，因此不能证明生产可靠性。生产中的 replan 还必须受第 7 章的工具白名单、审批、资源锁与执行预算约束。

若某动作可能产生不可逆副作用，重规划时不能因为上一次操作超时就直接再执行。要先检查幂等键、已生效的真实业务状态及补偿策略。

5. 将 Planning Events 写入第 5 章的 Run State/Event Store。
6. 为重复修订设置 max_replans、循环状态哈希和停止规则。
7. 使用第 7 章 AsyncToolRuntime 执行多个无依赖且已授权的只读步骤。
8. 在真实 Coding Agent 基准上比较无规划、静态规划、动态重规划和 Verifier 四组消融。

## 10.13 总结

Planning 解决长程目标和依赖，Execution 产生真实环境反馈，Replanning 处理未知分支和失败，Verification 决定任务是否满足验收。系统不能把“模型说完成了”当成“真实任务已经完成”。
